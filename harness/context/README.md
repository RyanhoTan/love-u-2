# Phase context guidelines

每个已经启动并获批准的阶段最多维护一个上下文文件：

```text
harness/context/phase-<NN>-<phase-slug>-context.md
```

只有当遗漏某条信息可能改变后续范围、实现、验证、安全或决策时才记录它。

## 应记录

- 用户决定、澄清以及明确的非目标。
- 影响实现的假设、架构或接口决定及其理由。
- 必须保持的行为、不变量、依赖和所有权边界。
- 安全、隐私、可靠性、回滚和恢复约束。
- 无法获得的验证证据、已接受限制、阻塞项和未知问题。
- 会影响后续阶段的发现，以及被替代的决定和替代理由。

尽可能引用具体文件、命令、测试结果、评审发现或用户决定。

## 不应记录

- 会话逐字稿、常规命令输出或逐步叙述。
- 没有长期影响的临时探索和失败尝试。
- 已由 goal、plan、phase 文件或 build log 持有的完整内容。
- 大段源码、diff、测试输出或计划副本。
- 没有依据的推测。
- 凭据、令牌、签名地址、连接字符串、个人数据或其他敏感值。

## 与其他文件的边界

- 阶段文件持有已批准范围、非目标、验收标准和计划验证。
- phase context 持有实质性发现、决策、约束和未解决问题。
- build log 持有实际进度和观察到的验证证据。
- code review artifacts 持有详细评审发现和签收状态。

在阶段交接前，删除无关叙述和重复内容，确认每个重要决定有理由和来源，并记录其对后续阶段
的影响。context 完整本身不代表阶段完成。
